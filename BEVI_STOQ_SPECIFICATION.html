Executive Summary

Bevi Stoq is a professional-grade inventory management system integrated into the existing BeviGrow web application. It enables users to manage products, track stock across multiple locations, handle customer requirements, and maintain complete inventory history.

Key Objective: Provide a scalable, data-driven inventory system that works for ANY product type without hard-coded categories, products, or locations.

Communication: The Customers module can CREATE requirements in Bevi Stoq, which then affects inventory. But customer data and stock data remain cleanly separated.

Key Design Principles

🚨 CRITICAL PRINCIPLES (Non-Negotiable):

1. Zero Hard-Coded Data

  • NO hard-coded categories like "Spices", "Coffee", "Masala"
  • NO hard-coded products like "Pepper", "Cinnamon"
  • NO hard-coded locations like "Yercaud", "Salem"
  • Everything must be user-created and configurable
  • Examples in documentation are only examples

2. Location-Based Stock (Not Global)

  • Every product must have stock tracked by location
  • Example: Pepper = 250kg (Yercaud) + 100kg (Salem) + 50kg (Chennai)
  • Never maintain a single global quantity for a product
  • Total stock = sum of all location stocks

3. No Negative Stock

The system MUST prevent negative inventory at all costs.

If available stock is 500kg and someone tries to reserve/consume 600kg, show:

  • Required: 600kg
  • Available: 500kg
  • Shortage: 100kg
  • Status: CANNOT FULFILL

Never silently create -100kg inventory.

4. Reserved vs Physical Stock

Example:

Physical Stock = 500kg | Reserved Stock = 100kg | Available = 400kg

Formula: Available = Physical - Reserved

When customer requirement is reserved, available decreases but physical remains unchanged. When fulfilled, both decrease.

5. Per-Product Low-Stock Thresholds

  • Each product has its own configurable low-stock threshold
  • Example: Pepper threshold = 50kg, Cinnamon = 20kg, Cardamom = 10kg
  • Status is calculated automatically based on current stock vs threshold
  • User does NOT manually select status

6. OUT OF STOCK = RED & OBVIOUS

When stock = 0kg:

Show "OUT OF STOCK" in RED/ERROR color throughout the application

  • Dashboard
  • Product lists
  • Category details
  • Location details
  • Customer requirement checking
  • Search results
  • Combo availability

Do not rely only on an icon. Make it impossible to miss.

7. Historical Integrity Must Be Preserved

  • All stock movements must be recorded
  • History is never deleted, only archived
  • If a category/product/location is deactivated, historical records remain intact
  • Audit trail shows: User, Date/Time, Quantity, Movement Type, Reference

8. Stock Changes via Transactions, Not Direct Editing

  • Avoid allowing users to directly edit quantities
  • All stock changes happen through proper transactions:
    • Add Stock
    • Transfer Stock
    • Reserve (Customer Requirement)
    • Fulfill (Customer Requirement)
    • Adjustment (Administrative only)
  • Each transaction creates an immutable movement record

9. Dashboard = Summary → Click = Details

  • Dashboard shows high-level summaries
  • Everything clickable for drill-down
  • Example: Click "Spices" → see all spices → click "Pepper" → see Pepper details

10. Atomic Transactions

  • Operations like transfers must be all-or-nothing
  • No partial success
  • If one part fails, entire transaction rolls back

Critical Calculations

Available Stock = Physical Stock - Reserved Stock Current Status = NORMAL if Available > Low-Stock Threshold Current Status = LOW STOCK if Available ≤ Low-Stock Threshold AND Available > 0 Current Status = OUT OF STOCK if Available = 0 Maximum Combo Possible = MIN(Available[Product1] / Combo.Qty1, Available[Product2] / Combo.Qty2, ...)

Product Management

Scope: CRUD operations for products with detailed configuration
  • Create Product - Name, Category, Default Unit, Low-Stock Threshold, Notes
  • Edit Product - Change all fields except unit (to prevent inconsistency)
  • View Products - List, filter by category/location/status
  • Search Products - Smart autocomplete with recent items
  • Duplicate Prevention - Warn if similar product exists in category
  • Activate/Deactivate - Soft delete
  • Delete Safety - Cannot delete if stock exists

Location Management

Scope: CRUD for warehouses/storage facilities
  • Create Location - Name, Description (optional)
  • Edit Location - Change name/description
  • View Locations - List with total stock
  • Search Locations - Partial name matching
  • Activate/Deactivate - Soft delete
  • Delete Safety - Cannot delete if stock exists

Stock Management

Scope: Core inventory operations
  • Add Stock - Product + Location + Quantity + Optional Reference
  • View Stock - By product, by location, by status
  • Stock by Location - Show breakdown for each product
  • Stock Transfer - Move between locations (atomic)
  • Stock Adjustment - Admin-only with reason/documentation
  • Prevent Negative Stock - Block any operation causing negative inventory
  • Track All Changes - Every change creates movement record

Stock Movements & History

Scope: Complete audit trail
  • Movement Types: Opening Stock, Added, Transfer In/Out, Reserved, Fulfilled, Return, Damage/Wastage, Adjustment
  • Movement Record: Date, User, Product, Location, Type, Quantity, Reference, Notes
  • View History: Searchable, filterable by date/product/location/type
  • Product Detail History: Show movements on product detail page
  • Audit Trail: Traceable to user and date/time

Customer Requirements

Scope: Track customer needs and availability
  • Create Requirement - Customer + Products + Quantities
  • Automatic Availability Check - Real-time calculation
  • Statuses: Pending, Available, Partially Available, Shortage, Reserved, Fulfilled, Cancelled
  • Reserve Stock - Lock stock for requirement
  • Multi-Location Allocation - Suggest optimal location allocation
  • Fulfill Requirement - Deduct actual stock
  • Cancel Requirement - Release reserved stock

Product Combos

Scope: Bundled product sets
  • Create Combo - Name + Product list with quantities
  • Edit Combo - Change products/quantities
  • Combo Availability Check - Show if all products available
  • Maximum Possible - Calculate max complete combos
  • View Combos - List with availability status
  • Saving Combo = No Stock Impact - CRITICAL: never modify inventory
  • Use in Requirements - Allow customers to request combos

Dashboard & Analytics

Scope: High-level overview with drill-down
  • Summary Cards: Total Stock, Low Stock Count, Out of Stock Count, Pending Requirements

Workflow Examples

Workflow 1: New Product + Initial Stock

1. Admin creates Category "Spices" 2. Admin creates Product "Pepper" - Category: Spices - Default Unit: kg - Low-Stock Threshold: 50 kg 3. Admin creates Location "Yercaud Warehouse" 4. Admin creates Location "Salem Warehouse" 5. Admin "Add Stock" → Pepper, Yercaud, 250 kg - Creates Movement: Opening Stock, +250 kg 6. Admin "Add Stock" → Pepper, Salem, 100 kg - Creates Movement: Opening Stock, +100 kg RESULT: Dashboard shows: Pepper = 350 kg total Spices category shows: Pepper 350 kg (NORMAL)

Workflow 2: Customer Requirement & Reservation

1. Requirement created: ABC Foods needs Pepper 200 kg 2. System checks: Available = 350 kg, Required = 200 kg - Status: AVAILABLE, Shortage: 0 3. Admin clicks "Reserve" - Physical: 350 kg (no change) - Reserved: 200 kg (increases) - Available: 150 kg (decreases) 4. Dashboard now shows: Low Stock alert 5. When fulfilled: - Physical: 150 kg (decreases) - Reserved: 0 kg (clears) - Available: 150 kg - Creates Movement: Fulfilled, -200 kg

Workflow 3: Stock Transfer Between Locations

BEFORE: Yercaud = 250 kg Salem = 100 kg Transfer: 30 kg from Yercaud to Salem AFTER: Yercaud = 220 kg Salem = 130 kg Creates TWO movements: - Transfer Out: Yercaud, -30 kg - Transfer In: Salem, +30 kg (Atomic - both succeed or both fail)

Workflow 4: Out of Stock Detection

Current: Pepper = 45 kg (Threshold: 50 kg) Status: LOW STOCK ⚠️ (Yellow) After fulfilling 45 kg: Current: Pepper = 0 kg Status: OUT OF STOCK 🔴 (Red - obvious) Dashboard: Shows RED badge Product List: Shows RED badge Category Detail: Shows RED badge Requirement Check: Cannot be selected Combo Check: Marked insufficient

Workflow 5: Combo Creation & Use

1. Admin creates Combo "Home Coffee Combo" - Robusta Beans: 500 g - Coffee Powder: 250 g (Saving = NO stock changes) 2. Dashboard shows availability: Robusta: 5 kg → can make 10 combos Powder: 1 kg → can make 4 combos Maximum: 4 combos 3. Customer needs: Home Coffee Combo × 10 Status: SHORTAGE (need 4 combos but only 10 available) Shortage: Powder insufficient

Workflow 6: Partial Availability Allocation

Requirement: 600 kg Pepper Available: 750 kg total - Yercaud: 400 kg - Salem: 250 kg - Chennai: 100 kg Suggested Allocation: - Yercaud: 400 kg - Salem: 200 kg Total: 600 kg (100% fulfilled) Remaining: - Salem: 50 kg - Chennai: 100 kg Admin reviews and approves → creates reservations

Performance Optimization

  • Avoid N+1 queries - Batch fetch related data
  • Indexed queries - Product ID, Location ID, Status fields
  • Pagination - Lists show 50 items, load more on scroll
  • Caching - Cache dashboard data (5-10 min TTL)
  • Debounced search - 300ms debounce on autocomplete
  • Aggregation queries - Sum stock by location, not loop

Concurrency & Transactions

Critical: All stock operations must be transactional
  • Use database transactions for all mutations
  • Recheck stock availability server-side (not just frontend)
  • Prevent double-reservation with row-level locking if needed
  • Atomicity: All or nothing for transfers
  • No partial stock updates

Database Design

Schema Overview

These entities should be created/migrated properly. Inspect existing schema first - do not duplicate if similar structures exist.

TABLE categories id (PK) name (UNIQUE in active) description active (default true) created_at created_by_user_id (FK) TABLE products id (PK) name category_id (FK) default_unit low_stock_alert_level (numeric) active (default true) created_at created_by_user_id (FK) TABLE locations id (PK) name (UNIQUE) description active (default true) created_at created_by_user_id (FK) TABLE inventory id (PK) product_id (FK) location_id (FK) physical_stock (numeric, default 0) reserved_stock (numeric, default 0) updated_at updated_by_user_id (FK) UNIQUE(product_id, location_id) TABLE stock_movements id (PK) product_id (FK) location_id (FK) movement_type (enum: 'opening', 'added', 'transfer_in', 'transfer_out', 'reserved', 'fulfilled', 'adjustment') quantity (numeric) unit (varchar) reference_id (nullable - FK to transfer/requirement) notes (nullable) created_at created_by_user_id (FK) TABLE customer_requirements id (PK) customer_id (FK) status (enum: 'pending', 'available', 'partially_available', 'reserved', 'fulfilled', 'cancelled') created_at created_by_user_id (FK) TABLE requirement_items id (PK) requirement_id (FK) product_id (FK) quantity_required (numeric) unit (varchar) quantity_reserved (numeric, default 0) quantity_fulfilled (numeric, default 0) TABLE combos id (PK) name (UNIQUE) description active (default true) created_at created_by_user_id (FK) TABLE combo_items id (PK) combo_id (FK) product_id (FK) quantity (numeric) unit (varchar)

Indexes

  • product_id on inventory (for stock lookups)
  • location_id on inventory (for location drill-down)
  • product_id on stock_movements (for history)
  • location_id on stock_movements (for location history)
  • customer_id on requirements (for customer lookups)
  • category_id on products (for category drill-down)
  • status on requirements (for filtering)

Data Integrity Constraints

  • Foreign key constraints (referential integrity)
  • NOT NULL on critical fields (product_id, location_id, quantity)
  • CHECK constraints on quantities (>= 0 for reserved/physical)
  • UNIQUE on product-location combination (no duplicate inventory records)

Validation Rules

Frontend Validation (User Feedback)

  • Product Name: Required, max 255 chars, no leading/trailing spaces
  • Category: Required, must exist
  • Unit: Required, must be from valid list
  • Low-Stock Threshold: Required, must be numeric, >= 0
  • Quantity: Required, must be numeric, > 0 (except adjustments)
  • Location: Required, must exist

Backend Validation (Security)

  • Re-validate all data server-side
  • Check authorization (user can perform action)
  • Verify foreign keys exist
  • Prevent duplicate categories (unique within active)
  • Prevent duplicate products (within category)
  • Check stock availability before transfer/fulfillment
  • Validate unit compatibility for conversions
  • Ensure no negative stock

Special Validation

Stock Transfer:
  • From location must have enough stock
  • Cannot transfer from same location
  • Both locations must exist
  • Product must exist
Customer Requirement:
  • Customer must exist
  • At least one product required
  • All products must exist
  • Quantities must be positive
  • Units must be valid
Requirement Fulfillment:
  • Requirement must exist
  • Requirement must be RESERVED
  • Stock must still be available (re-check)
  • Cannot fulfill amount greater than reserved
